# Issue #4：实时预览可行性原型

## 要回答的问题

Windows x64 的 WebView2 能否持续低延迟解码并显示 MuMu 12 经当前已验证 ADB 传输的 1280 × 720 H.264 画面，同时维持安全取点与显式点击语义？

本文件记录原型，而不是支持声明。原型实测门槛未全部通过前，不应把这条路径作为正式实时预览实现。

## 原型结构

- Rust `DeviceManager` 的内部预览进程适配器通过结构化参数启动 `adb -s <serial> exec-out screenrecord --output-format=h264 --size 1280x720 --bit-rate 8000000 -`，不经过 shell；连续 8 秒没有码流数据会终止会话。
- 预览子进程由 `PreviewController` 独占；停止、切换活动设备、更换 ADB 与应用退出都会中止它。
- Tauri `Channel` 直接传输二进制 H.264 块，不使用 Base64，也不启动 HTTP 服务或端口转发。
- Vue 将 Annex-B NAL 单元组装为 access unit，使用 SPS 得到 codec profile，通过 WebCodecs `VideoDecoder` 解码到 Canvas。
- 解码队列超过两帧时清空积压并等待下一关键帧，优先恢复到最新画面。
- 预览使用固定 1280 × 720 坐标面；单击只选择坐标，只有“执行点击”才发送 ADB tap。

`screenrecord` 存在设备相关时长限制、缺少正式断线状态回传且不是最终 scrcpy 式服务器，因此只用于验证 WebView2 解码路线。若达标，正式实现需用固定版本、许可证清晰的设备端持续编码组件替换采集端；若不达标，再单独比较 Windows 原生解码。

## 已知风险与下一决策

- WebCodecs 与 H.264 hardware acceleration 的实际可用性取决于目标 WebView2 Runtime、GPU 驱动与系统媒体组件。
- 原型使用固定编码尺寸，尚未从码流 SPS 提取旋转后的显示尺寸；方向变化验收未完成。
- `screenrecord` 自然退出、读取失败或码流停滞会触发统一的结束事件并自动回退；目前尚未区分具体退出原因。
- Tauri Channel 保序传输原始码流块；只有解码队列积压后才在 access-unit 边界丢帧，Windows 实测需确认 IPC 不会成为延迟瓶颈。
- 未引入、复制或打包 scrcpy 代码与产物，因此当前无需新增第三方许可证；正式采集方案必须另行 ADR 决策。
